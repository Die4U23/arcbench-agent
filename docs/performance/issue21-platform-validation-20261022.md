## 候选 7180b9a：浏览器验证器的进程退出竞态

[提交 507d76c3bbb2](https://arc-bench.com/playground/task-bank/web/ticketbooking/submissions/507d76c3bbb2) 使用包 SHA256 `f50094ef540f29e8354622f7edad317cc8a45c90cee61b19d5ec2f214afac901`，对应 CI 39743472775 通过。离线依赖边界已通过持续运行验证；16:33:33 的检查显示构建、前后端自测、完整公开交互重建均通过，但独立原生浏览器检查仍报告 `Address already in use`。这不是正式 30/30。

同一错误此前间歇出现，16:36:29 又使控制器将已通过公开重建的候选判为“行为结果不可用”，回退到此前 30/36 本地用例通过的版本。因此请求取消该轮，不能把不可靠的验证器反馈继续当作业务缺陷消耗模型请求。取消完成和最终用量以平台日志为准。

根因是两个顺序执行的原生验证阶段之间重新启动服务器：清理逻辑对进程组发送 SIGTERM，却只等待 npm 父进程。父进程退出不等于 Node 子服务器已经关闭监听。隔离 Docker 复现中，旧清理仅 0.001 秒便返回，端口仍被延迟退出的子进程占用。

修正是在已拥有并停止的服务器之后确认端口实际释放，最多等待 5 秒；超时只对该服务器的进程组发出 SIGKILL，再等待 1 秒。启动前发现已有监听的路径仍然拒绝启动，不会终止未知进程。清理最终失败以 `owned_server_cleanup_failed` 贯穿 worker、Docker 和认证网关，触发整轮基础设施停止，避免模型修复风暴。所有业务断言、公开测试和通过门槛均未改变。

新增真实 Linux 进程回归覆盖子进程延迟退出、忽略 SIGTERM 两种情况，并验证最终无法释放端口时的有界升级和致命错误，以及网关保留该错误原因且不重试。该修正不热替换正在运行的候选镜像，需以新提交、新上传包重新验证。

修正后本地全量 554 项中 538 通过、16 按环境跳过；另在新镜像中运行的 3 项 Linux 端口回归全部通过，11 项真实 Docker/认证传输集成全部通过。平台取消按钮触发原生确认框后浏览器工具失去响应，因此同时关闭旧隧道以阻止继续提交沙箱任务。构建新镜像改变了本地镜像标签，旧网关的镜像一致性检查也会拒绝后续任务，不会执行混合版本；最终停止原因必须以后续取回的平台日志为准。
