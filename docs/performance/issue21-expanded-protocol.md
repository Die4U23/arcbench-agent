# #21 扩大样本验证（2026-10-21）

本轮先冻结候选，再运行完整矩阵，最后才提交 ArcBench。只使用 Flash；按供应商 token 和完整任务成功率评估，不查询账户费用。

## 冻结设计

- 基线为上一轮候选 `d3d5e6eaf14dc770df709cdf2b031fa162d0e54c`，不是早期较弱版本。
- 候选只增加有界初始文件名清单、失败堆栈指向的原始源码片段。完整需求、显式读取、源码复用失效规则及受保护验收不变。
- 三个固定独立任务：金额与发票契约、库存事务与不可变输入、过滤排序与分页。均从相同错误源码开始，每次先确认 build 通过、固定验收失败。
- 每个任务基线和候选各 4 次，共 24 次；先按重复编号轮转任务，各任务奇数轮基线在前、偶数轮候选在前。必须保存失败，不删样本，不只报告最好的一次。
- 温度 0、thinking 关闭、输出上限 4,096，每次最多 12 个模型请求；相同 Docker image ID、需求、初始文件、验收脚本和机器。生成代码只在 Docker 内执行。
- 独立新研究使用 `--expanded`：合计 400 万 token、288 个请求，旧研究的 611,034 token 保留为历史。未知 usage、非 Flash 响应、验收被改写或基础设施异常停止；连续两次任务失败暂停排查，不自动追加样本或扩大额度。
- 试验期间不修改源码和验收、不同时跑资源密集测试。失败后如需改候选，先结束本矩阵并保留分母，重新标记后续试验，不混为同一版本。

## 指标与接纳

主要指标为同任务通过数、每成功任务输入与输出 token（失败消耗也计入）、请求数、实际修复轮次。辅以未缓存输入、加权缓存命中率、工具调用分布、重复读取和首次验收结果。命中率不能抵消正确率下降。

小型修复矩阵不等于整站构建速度或 30/30。最终候选需要重新运行平台自测及正式 30 个用例，并保留实际模型、源码/包哈希、提交 ID、原始结果和 token 用量；历史冻结成绩不能代替新成绩。

执行入口为 `scripts/run_token_trial.py --execute --expanded`，凭据仅经环境变量传入。逐次响应、生成源码、完整日志与结果保存在 `local-runs/issue21-expanded-20261021/`，公开报告只包含脱敏 usage、结果和证据哈希。
