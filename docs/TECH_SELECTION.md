# ARC-Bench 软件工程 Agent：框架与技术选型

> 版本：0.1（与 PRD 0.1 对应）  
> 适用阶段：项目启动、Demo Track、Normal Track 早期  
> 状态：初步方案；需以官网下载 starter 的实跑结果校正

## 1. 选型结论

第一阶段采用 **Python + 显式流程编排 + 小型受控工具集 + 实际构建/测试反馈 + ARC-Bench Runtime SDK**。先完成一个可复现的端到端任务，再根据评测和失败案例决定是否增加框架或更换编码后端。

| 范围 | 初步选型 | 依据与边界 |
|---|---|---|
| Agent 入口 | Python `main.py` + `requirements.txt` | 符合用户提供的 Runtime API 上传约定 |
| Python 版本 | 3.10+ | 空白 starter 的 Runtime SDK `pyproject.toml` 声明 `requires-python >=3.10`；Runner 实际版本仍需验证 |
| 平台运行时 | starter 随附 `arcbench-agent-runtime`，经其高层 API 操作 | 空白 starter 的 `requirements.txt` 引用 `./arcbench-agent-runtime`；保留本地 SDK 依赖，不能假定任意平台环境都预装该包 |
| 模型调用 | starter 示例采用 `openai` Python 包 | 示例读取 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`MODEL`；可选 `VISUAL_MODEL` 处理图片参考，服务须支持图像输入，具体能力需验证 |
| 需求读取 | `PyYAML` + Markdown 结构解析 + 标准数据结构 | 支持 `requirements.yaml` 与 ArcBench README 任务说明，并归一化成同一需求树；图片参考由规划阶段做多模态输入 |
| 流程编排 | 自研显式状态机/流水线 | 阶段顺序清晰、状态上报可与真实步骤对应；初期不引入重型 Agent 框架 |
| 本地开发 | `venv` 或 `uv`，开发依赖单独管理 | 平台入口依赖与本地开发工具分开，避免无必要增加上传包依赖 |
| 测试与质量 | `pytest`、`ruff` 作为开发期候选工具 | 仅在开始实现后启用；不要求目标应用必须使用 Python 测试框架 |

这里的“选型”是项目建议，不代表所有条目已在 ARC-Bench 运行环境验证。依赖版本、模型工具调用支持、网络与资源限制需在 starter 验证阶段确认。

## 2. 总体架构

```text
ARC-Bench Runner
  └─ 启动 Python Agent，传入任务目录、输出目录、任务类型和模型环境变量
       └─ main.py：解析参数、校验目录、建立运行上下文
            └─ Orchestrator：显式控制阶段与预算
                 ├─ Requirement Reader：读取需求并保留节点 ID
                 ├─ Planner：形成可执行步骤
                 ├─ Coder Backend：调用模型/工具修改目标项目
                 ├─ Verify：执行构建和测试，形成结构化结果
                 ├─ Repair：按预算根据失败反馈修复并重测
                 └─ Runtime Adapter：调用 ARC-Bench SDK 更新状态、追踪和 Git
                      └─ Runner 监听 SDK 事件并刷新平台界面

目标项目（输出目录）
  └─ 首阶段候选：官网 Web 模板（React/Vite + Express/SQLite）
```

### 2.1 设计原则

1. **流程由 Agent 程序控制**：需求读取、实现、验证和交付有明确阶段；模型负责阶段中的分析和代码工作，不自行决定是否跳过真实验证。
2. **状态由执行事实驱动**：只有构建/测试模块根据实际执行结果返回结果后，才允许上报测试通过或失败。
3. **接口薄而可替换**：模型客户端、编码后端、验证器和 Runtime SDK 适配层保持边界，避免更换实现时重写主流程。
4. **本地与平台共用主流程**：允许用本地任务目录调试；平台和离线模式都使用随包 Runtime SDK。离线模式不能替代平台验收。
5. **预算可配置**：限制模型调用次数、修复轮数和单条命令耗时；具体值待平台约束与实验基线确认。

## 3. 运行流程

建议的第一版主流程：

1. 解析 Runner 参数，检查需求目录和输出目录。
2. 初始化 `AgentRuntime`，报告运行开始。
3. 读取需求树，保留原始节点 ID；按任务类型判断是新建应用还是修改已有基线。
4. 为当前需求形成短计划，报告设计阶段完成。
5. 通过编码后端和受控工具修改目标项目，记录文件变更。
6. 根据目标项目已有脚本执行适用的构建和测试。
7. 若失败且仍有预算，向模型提供真实错误摘要，尝试修复并重新验证。
8. 根据最终命令结果报告测试状态；用 SDK 更新实际存在的需求、接口和测试追踪数据。
9. 按需使用 SDK 创建 Git 提交，整理结果摘要并报告运行完成；未处理异常则报告运行失败并以非零退出码结束。

阶段事件的具体可用方法以随包 SDK 的实际签名为准。API 文档明确禁止手工拼写 runner event payload；状态必须与执行事实一致。

## 4. 技术组件

### 4.1 入口与配置

- `main.py` 保持薄入口：解析参数、建立上下文、调用编排器、处理顶层错误和退出码。
- 按官方 CLI 约定接收需求路径、`--output-dir` 和 `--type`；默认值/参数位置以 starter 和平台运行实测为准。
- 使用标准库 `argparse`、`pathlib`、`logging`、`dataclasses`。初期不必为简单配置引入 Pydantic；当数据结构和校验需求确实增长时再评估。
- 日志写到 stderr 或独立日志文件；stdout 是否受平台截断需验证，不将平台协议事件写入普通日志。

### 4.2 模型调用与编码后端

模型客户端先按官网示例使用 `openai` 包读取注入环境变量。建议定义窄接口，例如 `LLMClient.complete(...)`，隔离 SDK 请求和响应解析。

编码后端暂列两种实现路径：

| 路径 | 说明 | 当前定位 |
|---|---|---|
| 自研受控工具循环 | 模型提出工具调用，Agent 执行读文件、搜索、编辑和验证命令，再把结果返回模型 | 候选主线；先验证当前模型与兼容端点是否支持所需工具调用，以及调用/上下文成本 |
| Codex/Claude 参考 Agent | 调用官网下载的对应 SDK/CLI 方案实现代码修改 | 参考或对比实验；依赖、权限、认证和运行环境必须实测，不能假设 Runner 已安装 CLI |

不在启动阶段同时维护两套编码后端。先完成一个最小任务的工具调用或参考 Agent 路径，再以平台成功率、失败可诊断性、成本和可控性做选择。若自研工具循环的模型端不支持 function/tool calling，可采用受约束的结构化响应作为降级方案，前提是解析与失败处理经过验证。

### 4.3 工具层

初期只提供完成任务必需的工具：

- 文件/目录读取与项目结构浏览。
- 文本搜索。
- 受控文件创建和编辑。
- 构建、测试及必要开发命令执行。

命令执行封装应固定工作目录、设置超时、限制输出大小并记录退出码。工具权限范围、命令策略和可执行程序需要服从 Runner 环境；不要把某份本地白名单写成平台保证。所有路径解析后必须确认目标位于授权的项目工作区，避免因模型输出路径造成越界写入。

### 4.4 目标应用栈

官网 Web 模板可作为 Demo 阶段候选，当前已检查的空白 starter 包含 React/Vite 前端和 Express/SQLite 后端，并包含 Vitest、Playwright 等测试依赖。它们是 **Agent 的目标项目栈**，不是 Agent 自身的 Python 依赖。

- 优先读取目标项目 `package.json` 中实际存在的 scripts，而不是假设统一命令。
- 前端/后端依赖安装是否由 Runner 负责、是否允许联网需实测。
- E2E 只有在模板、依赖、浏览器和平台执行环境均支持时才纳入首阶段验收。

**模板复制规则：**平台可能已在输出目录准备新项目模板或演化基线。Agent 应先探测输出目录并遵循平台约定；已有项目或基线时不得无条件复制覆盖。空目录时是否复制随包模板，也要通过官方 starter example 确认。

### 4.5 验证器

`Verify` 是 Agent 内唯一能生成构建/测试结论的组件。建议返回结构化结果，至少包括：命令、退出码、耗时、通过/失败状态和有限长度的输出摘要。

- 首先使用目标项目声明的 scripts 和测试框架。
- 若目标测试框架支持机器可读报告，优先解析该报告；否则至少依据真实退出码并保留原始输出摘要。
- 测试报告解析失败时应标记“结果无法解析/验证失败”，不能推断为通过。
- 修复循环轮数、命令超时、模型调用次数都应受预算约束。
- 演化任务尽量运行相关回归测试；基线对比能力后续按任务和平台证据扩展。

### 4.6 Runtime SDK 与 Traceability

实现 `RuntimePort` 或薄适配层，底层调用随 starter 提供的 `arcbench_agent_runtime`。依赖清单应保留 starter 的本地 SDK 引用形式（当前空白 starter 使用 `./arcbench-agent-runtime`），并按真实代码增加需求解析等必要依赖；不能仅因 API 文档称“built-in”就删掉随包 SDK。

- 将 run 状态与主流程开始/结束/异常边界关联。
- 将节点状态与相应需求阶段、真实实现和验证结果关联。
- 在已知且可验证时维护 requirement、interface、test 及其链接。
- 只通过 SDK 读写 traceability 和 Git；手工同步文件时按 API 文档调用高层刷新方法。
- 本地离线路径也调用真实 Runtime SDK，便于检查事件与 Traceability 写入；它不能替代平台端到端验收。

Git 提交策略不应预先强制“每阶段都提交”。先查看平台工作区的初始 Git 状态，按任务边界和课程展示需要提交有意义、可解释的快照；回滚和清理类操作仅在明确恢复场景使用。

## 6. 依赖管理建议

### 上传包运行依赖

以官网下载 starter 为起点，保留其实际需要的本地 Runtime SDK 和 `openai` 依赖。若 Agent 自己解析 YAML，则加入 `PyYAML`。不要机械照抄未验证的版本下限；优先使用 starter 锁定或课程提供的版本范围。

```text
./arcbench-agent-runtime
openai
PyYAML        # 仅在 Agent 直接解析 YAML 时需要
```

上例是逻辑清单而非已验证的最终锁定版本。实际 `requirements.txt` 应与所选 starter 保持兼容，并在平台依赖安装环境确认。

### 本地开发依赖

`pytest`、`ruff` 等工具可放入单独的开发依赖文件，避免扩大平台上传依赖。是否需要 `tenacity` 等重试库，等确认限流和重试语义后再决定；简单且有明确上限的重试也可先用标准库实现。

## 7. 分阶段技术路线

| 阶段 | 实施重点 | 暂缓内容 |
|---|---|---|
| 启动验证 | 解读 starter；核对 CLI、Python 版本、SDK 签名、输出目录和依赖安装；跑通官方模型示例 | 自研复杂工具循环、RAG、MCP、多 Agent |
| Demo | 入口、需求读取、单任务编排、实现、构建/测试、有限修复、SDK 状态和一份实验记录 | 多种编码后端并行维护、复杂测试报告平台、无证据的性能优化 |
| Normal | 分类处理构建/测试/超时错误，改善上下文读取、追踪完整度和预算控制 | 在没有任务规模或失败证据前引入向量库和复杂 Agent 图 |
| 期中后 | 扩展 Feature Enhancement 与 Testing & Bug Fixing，增加回归验证和基线保护 | 为技术新颖性而增加无关依赖 |
| Competition | 根据重复实验决定是否增强检索、并行验证或更换编码后端 | 仅凭单次结果做重大架构迁移 |

## 8. 实验与可观测性

每次实验至少记录：任务/Track、提交或运行标识、Agent 代码版本、模型与配置（不得保存密钥）、实际运行步骤、构建/测试结果、最终排名/状态、主要失败原因和下一步改进。

本地可以保存结构化日志或简明实验表。不要假设课程要求某个固定的 `runs/` 文件布局；先检查平台是否会采集工作区内容，以及是否有敏感信息清理要求。Prompt 和配置应纳入版本控制，但不要提交 API Key 或其他凭证。

## 9. 待验证技术清单

首次 starter 验证时确认并记录：

1. Runner 实际 Python 版本、CLI 参数、任务类型枚举和退出码处理。
2. 上传依赖安装方式，以及本地 Runtime SDK 路径依赖是否按 starter 方式安装。
3. `OPENAI_BASE_URL`、`MODEL` 对应服务是否可调用；是否支持 function/tool calling、JSON 输出及 Responses API。
4. Runner 提供的输出目录初始状态：空目录、预建模板、演化基线和 Git 状态。
5. Node/npm 可用性、依赖安装网络权限、前后端脚本、Playwright 浏览器是否存在。
6. 单次运行的时间、Token、调用次数和输出大小限制。
7. Traceability schema、需求节点 ID 和状态枚举要求，以及平台排名有效条件。

验证结果应回填到实验记录和 PRD，不以推测代替实测。

## 10. 选型决策记录

| 决策 | 当前状态 | 重新评估条件 |
|---|---|---|
| 使用 Python starter 与 Runtime SDK | 由用户提供的官方 Runtime API 与下载包支持 | 官方平台运行与文档出现不一致时，以课程确认结果修订 |
| 采用显式编排而非重型 Agent 框架 | 初步选择 | 分支/并行/恢复复杂度经实验确实难以维护时评估 LangGraph 等 |
| 编码后端选择自研工具循环还是参考 Coding Agent | **待首轮对比验证** | 对比平台兼容性、成功率、成本、透明度和修复能力后确定 |
| 使用 Web React/Express 模板 | Demo 候选 | 任务类型或平台推荐模板不匹配时调整 |
| 模型客户端使用 OpenAI Python 包 | 与空白 starter 示例一致 | 目标模型端点兼容性或依赖环境验证失败时换实现 |
| 使用测试 JSON reporter | 逐目标项目适配 | 只有当前测试框架支持且报告可靠时采用 |
