# #21 扩大 Flash 样本后的 token 与无效操作结果

2026-10-21 的最终固定对照完成 24 次：基线与候选各 12 次，均通过独立 build/test。候选总 token 减少 **61.64%**，未缓存输入减少 **42.22%**。结论只覆盖三个固定 CommonJS 修复任务，尚不能推算整站构建或平台 30/30 的节省。

## 固定比较条件

- 基线为上一轮最终版本 `d3d5e6eaf14dc770df709cdf2b031fa162d0e54c`，候选为 `0d9e0a93f87a653ec1baa55a60f88ad1207086b1`。
- 三个任务各运行四对，奇数轮基线在前、偶数轮候选在前；同一输入、受保护验收、Docker image ID、机器和请求限额。每次最终验收在 Docker 内独立执行，不采用模型自报结果。
- 全部 186 个请求的供应商响应均为 `deepseek-flash`，usage 完整；温度 0、thinking 关闭、每请求输出上限 4,096、每次试验最多 12 个请求。
- 本次确认矩阵没有同时运行资源密集本地测试；逐次源码哈希保持不变。设计与第一批失败后的调整见[协议](issue21-expanded-protocol.md)。
- 基线与候选均采用写入前保护，修改验收文件的尝试返回拒绝结果；写入后不变性检查继续保留。

## 改动为何有效，以及不能得出的结论

候选在稳定需求之后追加有界文件名清单，减少为找已知路径而产生的请求。失败脚本附带堆栈所指位置附近的原始源码，帮助直接比对返回值、调用者和断言。提示词明确复用充分的现有测试，并在必需实现与声明的 build/test 通过后交回独立控制器，避免成功后继续添加可选测试、尝试不存在的脚本或反复确认。

完整需求、显式刷新读取、受保护断言以及控制器完整验收仍保留。此前的批量源码复用仍按真实内容及可见消息验证；本次候选没有触发复用事件，因为它没有再次请求同一批文件。收益主要体现为避免发起多余操作，不能归因于缓存替换本身。

更少的请求意味着更少重复长前缀，所以命中率百分比下降，但总输入与未缓存输入同时下降。金额任务候选未缓存输入反而从 8,606 增到 11,468；跨任务合计才是下降 42.22%。本轮没有实现或承诺 99% 命中率，也没有通过填充重复输入制造该比例。

三个任务都很小，四次重复不是四个独立新任务；同一供应商缓存可能被前面的请求预热。服务耗时受网络与供应商波动影响。此处是固定交错矩阵的描述性结果，没有 Claude Code 同条件对照，也不足以宣称整站性能提高 61.64%。
