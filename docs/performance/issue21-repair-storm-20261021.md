## 现象、根因与收尾

1. 11:12 左右离线安装报 `ENOTCACHED`：旧锁文件需要 `esbuild@0.25.9`，原镜像主要缓存 0.25.12，未覆盖对应旧版包及本机架构二进制。
2. 后续安装出现 `spawnSync .../esbuild EACCES`。真实 Docker 探针确认 `/work`、`/tmp` 的 tmpfs 默认包含 `noexec`；镜像构建时的缓存检查未采用相同挂载条件，简单 React 安装没有执行原生依赖，未发现此问题。
3. 一些中间版本通过前后端自测和前端构建，但后续检查又退回依赖安装失败，公开交互回归未形成最终通过结论。
4. 工具批量调用、验证包装器和控制器将基础设施异常统一转换成业务修复反馈。模型反复修改、读取、检查；不同模块继续领取修复额度。这是控制流中的无效修复循环，不是供应商 HTTP 自动重试。
5. 为止损尝试取消运行时，浏览器确认操作卡住。11:33:34 本机网关和隧道先被关闭，用户随后确认停止。**关闭通道本身引入了后续 transport 错误**，不能把这部分错误归因于原始平台网络故障。
6. 关闭之后仍记录到 49 次完成响应，输入 1,764,720、输出 40,630。该时间分组可能含跨越关闭时刻的在途请求，不表示 49 次都在关闭后新发起，但足以证明旧控制器没有立即停止模型循环。11:37:20 控制器才以失败结束。

## 修复与日志约定

- 补齐旧版 esbuild 与当前 Linux 架构二进制缓存；真实运行的 `/work` 显式使用 `exec,nosuid,nodev`，支持构建工具原生执行。执行仍在非 root、断网、只读根目录、清空 capabilities、限资源的容器内，未开放宿主执行或 Docker socket；`/tmp` 保持 `noexec`。
- 缓存缺失、依赖执行权限异常、远端不可用、授权失效、镜像异常使用独立基础设施异常。worker 退出码 78、网关分类和客户端类型跨进程保留；通用工具错误捕获不得将它变成业务修复提示。
- 首次确认基础设施异常就结束整轮，不继续其他模块、检查点恢复、视觉评审或模型调用。普通业务测试失败仍保留正常修复通路。
- 输出结构化 `ARCBENCH_METRIC` 事件 `repair_circuit_opened`，并落盘 `.arc/infrastructure-failure.json`。字段含 `failure_kind`、`reason`、`occurrences`、`retry_count`、`action`、`model_requests`、`prompt_tokens`、`completion_tokens`。即时停止时发生次数为 1、重试次数为 0；缺失计量记 null，不补成 0。日志不包含远端 URL、Bearer 或模型 Key。
- 每次模型请求本身仍由现有 attempt ID 去重统计；不通过填充上下文来提高缓存比例。
