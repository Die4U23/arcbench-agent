## 第一轮改动（affd336）

该次修改前，任何有效文件写入都会同时清空 `epoch_reads` 与全部 `epoch_file_reads`。因此 `[a,b] → 修改 a → [b,c] → [b,a]` 中，仍在对话内且未变化的 b 会重新返回全文。改动限于：

- 写入后清除精确批次缓存，但文件摘要只失效被写文件，保留同一对话段内其他完整源码证据。
- 每个 `read_files` 都重新读取当前磁盘结果再比摘要，避免相同参数遮蔽外部改动/删除。
- 截断内容不做“完整文件未变”的判定；压缩、控制器回滚及强制源码刷新继续清空/失效原有证据。

没有删除上下文内容、降低验收、改需求或填充 token；文件只在它的完整内容仍可在当前对话段找到且重新读取相同时才返回 unchanged 提示。

## 离线验证

新增覆盖无关写入、重叠批次 `[a,b]→[b,c]→[b,a]`、相同批次外部改动/删除、变更后还原、截断边界；原检查点/压缩/thinking 协议测试继续通过。

使用仓库实际 `prompt_context.py` 和 `repair_policy.py` 作为只读夹具，基线 `d965116` 与候选运行完全相同的 5 次 fake 模型调用和文件操作。最终 a 都为 `value = 2`。累计序列化消息字符由 **118,868 → 116,242**（减少 2,626，约 2.21%）；请求数均为 5。结果保存在 `local-runs/issue21-offline-20261020/read-cache-proxy.json`，没有供应商请求。这只是该固定序列的上下文体积证据，**不是实际缓存命中率、token、费用或完成率改善**。

对照使用会自然涉及共享文件读取的固定修复任务，不额外要求无用读取。优先报告未缓存输入、总输入/输出、请求数、完整分母及包含失败消耗的每成功任务 token，缓存百分比只是其中一项。

## 第二轮历史候选：跨读取工具复用与重复需求去重

以 `9179d73` 为本轮代码基线。第一轮只对 `read_files` 建立文件摘要，`read_file`（包括行范围）仍重复发送相同源码；压缩时会连同仍保留的完整原文一起清空摘要。完整项目需求也会在当前模块子树中再序列化一次。

`bc7694f` 当时的改动如下，其中范围 ID 压缩已在后续真实试验后撤回：

- 单文件、完整批量读取共享证据；行范围只与相同路径和相同行范围复用。每次仍实际读取磁盘，检测外部变化、删除及权限错误。短内容不替换为更长的“未变”提示。
- 证据关联实际发送的工具消息。压缩时，只有原文仍被保留的证据继续有效；仅保留引用提示不算保留原文。回滚和强制源码刷新仍失效，写入只失效相关文件全部行范围。
- 截断或格式不完整的内容不建立完整源码证据；复用只减少新增工具结果，不重写历史消息前缀。记录不含源码的 `source_read_reused` 字符节省事件。
- 当前子树与完整需求中的唯一节点完全一致时，只发送范围 ID，并明确包含全部后代；附加修复约束、缺失或重复 ID 保留完整范围。完整项目需求本身不删减。

## 真实 Flash 对照：先计成功，再计节省

固定任务为 `benchmarks/issue21/shared-module-repair.json` 的三个 CommonJS 模块修复。保护 `package.json` 和验收文件，每次从相同错误源码开始；确认初始 build 通过、test 失败，生成代码只在固定 Docker 镜像中运行。最终由同一完整 build/test 判断通过，包含无效输入、边界、税额、折扣及输入不变性断言，不采用模型的自报结果。

- 基线源码：`9179d73cf7a10ec69e20cde10f75750b7963cb82`。
- 第一阶段候选：`ae1cdd7459aefcf00a1a34925d80ee45cb7ce34b`，Agent 与 `bc7694f` 相同。
- 第二阶段候选：`5d62407b23a8b6d406cc7bced5ec3ece2ed9c30e`，恢复完整需求，并复用成功完整写入的源码。
- 最终候选 v3：`8e32b42b56a4e5ad6735956c18108f549ff76d70`，显式 `read_file` 始终刷新全文，只复用批量读取。
- Docker：`sha256:3c9ee4121afa393a13ffa0d6d278b30545735781610e430aa2c4a08e7948296c`。
- 模型仅 `deepseek-flash`，温度 0，thinking 关闭，每次最多输出 4,096 token。每次最多 8 个请求。第一阶段每组 3 次，顺序为基线、候选、候选、基线、基线、候选；第二阶段原计划同样交错，但候选连续失败两次后停止。剩余 3 个试验槽位用于修正后的 v3，没有增加总请求或 token 上限。
- 两阶段合计 2,000,000 token，第二阶段只将请求上限从 48 扩至 96，不清空前次消耗或失败记录。每次发送前预留完整输入窗口加输出上限，未知 usage 不自动重试；默认不带 `--execute` 时零请求。

### 第一阶段：拒绝以正确率换 token

| 组别 | 通过 / 全部 | 请求 | 输入 token | 输出 token | 命中输入 | 未命中输入 | 输入命中率 | 每成功任务总 token（含失败） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 基线 | 3/3 | 24 | 151,435 | 6,457 | 142,592 | 8,843 | 94.16% | 52,631 |
| 候选 v1 | 2/3 | 24 | 141,016 | 4,302 | 133,760 | 7,256 | 94.85% | 72,659 |

候选总 token 少约 7.96%，但每成功任务消耗增加约 38.05%，因此不接受这组结果为优化成功。`candidate-1` 把折扣函数的“折后金额”实现成“折扣额”，受保护断言失败；完整源码和响应保留。该小样本不能确定是提示词压缩导致失败，但不足以支持发布该改动，因此撤回范围 ID 压缩。

该阶段所有试验都没有触发 `source_read_reused`，说明单纯读取证据缓存没有覆盖这里实际发生的“写入后再读取”路径。部分试验与本地单元测试重叠，耗时仅作诊断记录，不能作为性能因果结论。

### 第二阶段：保留完整需求，复用已经可见的成功写入

仅在完整写入成功、包含源码的 assistant 工具调用仍在当前对话内、后续实际读盘内容与写入内容完全相同时，用短提示代替重复全文。写入失败、实际内容被规范化、外部修改、删除、完整消息被压缩丢弃、控制器回滚或强制刷新时仍返回完整证据或真实错误；部分替换不作为完整文件证据。历史消息前缀保持原样。

第二阶段原始记录使用 `baseline-v2-*` / `candidate-v2-*` 标签，与第一阶段一同保留在 `local-runs/issue21-token-ab-20261020/`。每次包含最终源码、供应商原始响应、控制器日志、最终 `checks.json` 和 `result.json`。`token-usage.json` 只统计 token 和请求，不查询或推算账户费用。

第二阶段基线 1/1 通过，候选 0/2 通过，因此停止原定后续调用。两次候选分别在折扣返回值、发票折扣含义处失败。共触发 3 次源码复用，但模型收到单文件 unchanged 后，改用行范围读取相同文件，消耗了原本可用于修复的请求。不能证明所有失败由复用引起，但这是可观察且应消除的额外调用。

### 最终候选 v3：给显式刷新保留完整内容

将 `read_file` 作为显式刷新，无论完整文件或行范围，都返回实际读盘结果。它仍可为后续批量读取提供完整文件证据，但自身不会被 unchanged 替换。对批量读取保留已发送源码、成功完整写入源码和压缩后的证据关联。

| 组别 | 通过 / 全部 | 请求 | 输入 token | 输出 token | 命中输入 | 未命中输入 | 输入命中率 | 每成功任务总 token（含失败） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 全部基线 | 4/4 | 32 | 201,149 | 8,152 | 190,208 | 10,941 | 94.56% | 52,325 |
| 候选 v1（撤回） | 2/3 | 24 | 141,016 | 4,302 | 133,760 | 7,256 | 94.85% | 72,659 |
| 候选 v2（撤回） | 0/2 | 16 | 98,759 | 2,285 | 94,848 | 3,911 | 96.04% | 无成功样本 |
| 最终候选 v3 | 3/3 | 24 | 150,269 | 5,102 | 143,744 | 6,525 | 95.66% | 51,790 |

全部 12 次试验共 96 个请求，输入与输出合计 **611,034 token**，其中失败也完整计入。v3 三次分别消耗 50,977 / 51,328 / 53,066 token，均通过受保护 build/test；共 1 次批量读取复用。对照全部基线，每成功任务总 token 描述性下降约 1.02%，未缓存输入均值从 2,735 降至 2,175（约 20.48%），命中率提高约 1.10 个百分点。

这些差值**不构成可靠的因果性能结论**：v3 是查看失败后形成的适应性修正，执行顺序不是重新随机交错，样本仅 3 次、只有一个任务，服务商缓存可能随先前运行预热；不能把输出路径随机变化的收益全部算给源码复用。v2 的最高命中率却对应 0/2 成功，说明必须把成功率和每成功任务 token 放在前面。

最终版本重放原有两组合成离线序列时，消息字符均为 500,527，新增前缀字符均为 92,222；比基线各增加 9 个字符，来自更长的读写复用提示。工具轨迹、最终文件哈希、完整需求上下文与基线一致。此前 23.93% 的离线降幅不再属于最终实现，也不宣称当前版本在该序列中节省 token。

可审计的逐次 usage、结果 SHA256 与汇总保存在仓库 [token-results-20261020.json](../../benchmarks/issue21/token-results-20261020.json)；完整响应、生成源码与日志只保留在本地试验目录。最后未发生第三阶段额外额度扩容。

这是合成修复任务，不能替代最终候选的平台 30/30、跨任务成功率或 Claude Code 对照，也不能据此承诺 99% 命中率。旧的冻结交付物保持独立。
