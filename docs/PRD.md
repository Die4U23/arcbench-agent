# ARC-Bench 软件工程 Agent 项目 PRD

> 版本：0.1（课程项目初稿）  
> 状态：基础架构已初始化；待小组确认与 ARC-Bench 首次运行验证  
> 项目：CS3604 Agentic Software Engineering

## 1. 项目概述

本项目面向 CS3604 课程，设计、实现并持续改进一个能够在 ARC-Bench 上运行的软件工程 Agent。Agent 接收平台提供的软件需求或演化任务，理解任务并规划修改，操作目标应用，运行构建与测试，根据验证结果继续修复，最后交付实现和过程证据。

项目评价不以“生成了一个应用”为终点，而关注 Agent 能否完成可验证的软件工程任务，并能依据失败结果迭代。项目后续覆盖从零生成、Feature Enhancement、Testing & Bug Fixing 等任务类型。

团队为双人小组，符合课程每组不超过 3 人的要求。课程目标包括在 ARC-Bench Demo、Normal 和 Competition Tracks 逐步获得有效排名，并完成期中汇报、期末展示及最终材料提交。

## 2. 背景与问题

大语言模型可以生成代码，但单次生成无法保证需求覆盖、构建成功、测试通过或修改后旧功能仍然正常。软件工程 Agent 需要把自然语言任务转成结构化工作，并通过工具调用、测试、反馈和版本管理约束生成过程。

ARC-Bench 提供任务运行和评测环境。其 Runtime SDK 提供运行状态、需求状态、Traceability 和 Git 操作接口，并通过 runner event stream 通知平台刷新状态、追踪面板和提交/预览信息。因此，本项目需要同时处理两件事：完成目标软件任务，以及将执行过程按平台协议报告。

## 3. 项目目标与非目标

### 3.1 项目目标

1. 提供符合 ARC-Bench 上传入口约定的 Agent。
2. 建立“需求读取—规划—实现—构建/测试—修复—交付”的最小闭环。
3. 使用 `arcbench_agent_runtime` 报告运行与需求状态，维护 Traceability，并按需进行 Git 操作。
4. 先完成可运行的 Web 生成任务，随后扩展至 Feature Enhancement 和 Testing & Bug Fixing。
5. 通过 Track 排名、自动化测试、失败案例和可复现实验持续改进 Agent。

### 3.2 非目标（第一阶段）

- 不以搭建复杂多 Agent、RAG 或 MCP 系统作为 Demo 阶段前置条件。
- 不把某个 Web 模板本身当作课程项目的核心交付物；模板只是 Agent 操作的目标应用脚手架。
- 不将 SDK 状态上报等同于任务正确性证明；正确性需要由构建、测试和平台评测支持。
- 不在未验证前假设平台的隐藏运行细节、限制、测试 Oracle 或各 Track 评分规则。

## 4. 用户与使用场景

### 4.1 主要用户

- **课程小组成员**：开发、调试和分析 Agent。
- **ARC-Bench Runner**：按约定启动 Agent，提供任务目录、输出目录、任务类型和模型环境变量。
- **课程教师/评测平台**：通过评测结果、状态面板、Traceability、Git 提交和预览检查 Agent 的执行情况。

### 4.2 核心场景

1. Runner 启动 Agent，Agent 读取需求并实现一个 Web 应用或需求子树。
2. Agent 构建应用并运行测试；测试失败时分析反馈、修复并重测。
3. Agent 在已有应用上增加功能，并验证相关回归测试。
4. Agent 根据测试或缺陷描述定位问题、修复并报告结果。
5. 小组复现一次实验，记录任务、模型/配置、代码版本、测试结果和失败原因。

## 5. 系统边界与 API 框架

项目中有三类接口，职责必须区分：

1. **ARC-Bench 上传入口**：Python Agent 在提交包根目录提供 `main.py` 和 `requirements.txt`。Runner 按固定 CLI 形状启动入口，并传入任务路径、输出目录和任务类型等参数。Python Agent 的入口形式以课程提供的 Runtime API 文档为准。
2. **模型 API**：Runner 通过环境变量注入模型调用信息，例如 `OPENAI_API_KEY`、`OPENAI_BASE_URL` 和 `MODEL`。Agent 使用模型进行需求分析、规划或代码生成。实际模型可用性与具体调用接口应在官方 starter example 中验证。
3. **目标应用 API**：Agent 所修改的应用可以有自己的前后端 API，例如 React 前端调用 Express 后端的 `/api/...`。这些接口属于生成应用，不是 Agent 与 ARC-Bench 的平台接口。

### 5.1 ARC-Bench Runtime SDK

Agent 调用内置 `arcbench_agent_runtime` Python SDK。SDK 管理固定事件协议、`.arc/runner-events.jsonl`、`.arc/traceability/*.json` 和相关刷新通知。Agent 不手工构造事件 payload；应使用高层 API。

- **状态事件**：`mark_run_started/completed/failed/paused/resumed`；`mark_design_done`；`mark_implementation_done`；`mark_test_passed/failed` 等。
- **Traceability**：通过 `runtime.traceability` 初始化数据并维护 requirements、scenarios、interfaces、tests、node states、call edges 和 contracts 等记录。
- **Git 操作**：通过 `runtime.git` 初始化仓库、配置身份、提交、查看状态或在明确恢复场景下回滚/重置。
- **前端刷新**：SDK 写入追踪快照并追加事件；Runner 监听事件、读取最新数据并通知前端刷新状态、追踪、提交历史或预览。

### 5.2 执行数据流

```text
ARC-Bench Runner
  └─ 启动 main.py，传入任务与输出目录，并注入模型环境变量
       └─ Agent 读取 requirements.yaml
            ├─ 模型 API：分析需求、规划或生成代码
            ├─ 工具：编辑项目、构建、测试、修复
            └─ Runtime SDK：更新状态、Traceability、Git
                 └─ 写入事件与追踪快照
                      └─ Runner 后端监听并刷新平台前端
```

## 6. 功能需求

### FR-1：平台入口与参数处理

- Agent 应有可被 Runner 调用的根目录入口文件和依赖清单。
- 入口解析需求目录、目标输出目录和任务类型。
- 启动后应确认任务输入和输出目录可访问；输入不合法时以失败状态退出并给出可诊断信息。

### FR-2：需求读取与任务规划

- 读取当前任务所需的需求文件，不依赖手工硬编码某个任务 ID。
- 将需求转为可实施的模块/步骤，并保留需求标识与实现、接口、测试之间的对应关系。
- 若采用逐个子树处理等策略，应确保跨步骤共享同一目标目录和已完成工作。

### FR-3：代码实现与项目操作

- 能基于目标项目的现有结构实现需求；已有项目任务须尽量保留现有功能。
- 通过模型或编码工具完成具体修改，但 Agent 主流程负责控制任务范围、执行步骤和结果判定。
- 首阶段以官网包所含 Web 模板作为候选目标脚手架；是否复制模板需遵循 Runner 对输出目录的准备方式，避免覆盖平台提供的基线项目。

### FR-4：构建、测试与修复

- 实现后运行适用的构建和测试命令。
- 测试通过与失败均需如实记录；不得将未运行或失败的测试标记为通过。
- 失败时根据实际输出尝试修复并重测；保留最终结果和必要诊断信息。
- 演化任务需要关注相关回归测试，而不只验证新增行为。

### FR-5：运行状态与平台可视化

- 使用 Runtime SDK 报告运行开始与结束状态。
- 对需求节点按实际进展报告设计、实现和测试状态。
- 失败和暂停等情况使用对应 SDK 状态，不得用完成状态掩盖中断或失败。
- 不手工写 runner event payload 或 SDK 管理的 traceability 文件。

### FR-6：Traceability

- 为已理解的需求建立追踪记录。
- 当实现接口、函数或测试时，记录其与需求的关系及文件位置（在 SDK 字段允许且信息可确定时）。
- 测试运行后更新对应测试的通过状态。
- Traceability 应以实际产物为依据，不记录不存在的接口或未运行的测试。

### FR-7：Git 与交付

- 按需使用 SDK 管理 Git 仓库及身份。
- 提交应对应完整、可说明的实现阶段；不为制造活动记录而提交未经验证的状态。
- 完成时总结修改内容、构建/测试结果和已知问题，并确保 Runner 可正常结束 Agent 进程。

### FR-8：实验记录与迭代

- 每轮实验记录任务类型、任务标识、代码版本、模型/配置、结果、耗时或资源数据（可获取时）、失败原因和改进措施。
- 通过失败案例推动需求理解、规划、工具使用、测试设计和修复策略的改进。
- 对比改进前后的结果，避免仅凭单个成功案例宣称普遍提升。

## 7. 非功能需求

- **可运行性**：入口、依赖和运行命令符合 ARC-Bench 提交约定。
- **可验证性**：结论由真实构建、测试或平台评测结果支持。
- **可追踪性**：需求、实现接口、测试和 Git 变更尽可能建立明确关联。
- **可恢复性**：遇到模型、工具或测试错误时报告失败原因；支持时可安全重试或恢复。
- **预算意识**：记录并控制模型调用、Token 或运行时间预算；具体限额待课程/平台确认。
- **可维护性**：先实现清晰的模块边界和单一任务闭环，再根据评测证据增加 RAG、MCP 或多 Agent 等能力。

## 8. MVP 范围与验收标准

### MVP 范围

交付一个可上传运行的 Python Agent，使用 Runtime SDK 接入平台，完成至少一个 ARC-Bench Web 生成任务的读取、实现、构建/测试、状态上报和结果总结。遇到失败时能报告失败，并至少对可诊断的失败尝试修复或明确说明无法修复的原因。

### 验收标准

1. Runner 能按约定启动 Agent，Agent 能解析传入任务和输出目录。
2. Agent 确实读取当前任务需求，并在目标目录产生与需求相关的修改。
3. Agent 至少执行适用的构建或测试；展示中的通过/失败状态与实际命令结果一致。
4. Agent 使用 Runtime SDK 写入运行状态和相关需求状态；平台能根据事件/快照刷新对应视图。
5. 对已创建的接口和测试建立有依据的 Traceability 记录。
6. Agent 能正常退出；出现错误时以失败状态结束并给出有用诊断。
7. 至少完成一次可复现的 Demo Track 提交并取得有效排名，作为 Demo 阶段课程目标。

**证据要求**：保存提交/运行标识、代码版本、测试命令及结果、平台排名或状态截图/记录、主要失败和修复说明。具体证据格式以课程要求为准。

## 9. 课程阶段与交付物

| 阶段 | 目标 | 主要交付物 |
|---|---|---|
| 项目启动 | 双人组队，熟悉官方 starter 与 Runtime API | 项目结构、职责分工、接口验证记录 |
| Demo | 完成首个可运行 Agent，在 Demo Track 获得有效排名 | Agent、可复现运行记录、初步结果与问题清单 |
| 基础完善 | 提升稳定性，在 Normal Track 获得有效排名 | 更完整的需求—实现—测试—修复闭环、实验记录 |
| 期中展示 | 汇报架构、当前效果、问题和计划 | 架构说明、阶段数据、失败案例、下一阶段计划 |
| 后半学期迭代 | 增加 Feature Enhancement 与 Testing & Bug Fixing 能力 | 多轮任务实验、回归测试证据、改进对比 |
| Competition/期末 | 优化正确率、效率与工程能力，争取 Competition Track 有效排名 | 最终 Agent 源码、实验结果、项目材料和展示 |
| 期末后 | 最终展示后 10 天代码完善与提交期 | 修订后的最终代码与课程要求的补充材料 |

## 10. 双人协作建议

职责可以按能力模块先行划分，但关键链路需要两人共同理解和演示：

- **成员 A：Agent 与平台接入**——入口、需求读取、模型/编码工具调用、Runtime SDK、运行状态和 Git 集成。
- **成员 B：应用验证与实验**——目标应用结构、构建测试、测试反馈与修复验证、实验记录和失败分析。
- **共同负责**——架构决策、代码评审、Track 实验、期中与期末展示。每个阶段互相交叉检查，确保任一成员能解释端到端流程。

具体人员安排由小组确认，可随阶段调整。

## 11. 风险、依赖与待确认项

### 已有依据

- 用户提供的 ArcBench Runtime API 文档规定 Python 上传入口、SDK 用法、状态事件、Traceability、Git 和自动刷新机制。
- 官网下载包中包含空白 Agent、Codex/Claude 参考 Agent、Runtime SDK 和 Web 应用模板；本仓库当前保存这些 ZIP 文件。
- 课程大纲给出 Demo、Normal、Competition Track，期中/期末展示，Feature Enhancement 与 Testing & Bug Fixing 等课程目标。

### 待验证

- 在课程平台运行官网下载的 starter example，并核对当前账户、运行环境和入口参数行为。
- Runner 是否预先准备目标输出目录及演化基线；Agent 何时应复制本地模板，避免覆盖现有项目。
- 平台对 Python 依赖安装、Node 依赖安装、执行时间、Token/资源预算和网络访问的具体限制。
- 各 Track 的任务集、排名有效条件、评分/失败判定和可获取的实验数据。
- Traceability 各字段的完整 schema、需求节点状态枚举与测试 Oracle 规则。
- 双人小组的具体提交物、期中/期末评分细则及 10 天完善期的提交格式。

### 风险应对

- **协议误解**：优先运行官方 starter example，以平台实际运行结果校正实现。
- **状态与真实结果不一致**：状态由执行步骤和测试结果驱动，不手工伪造通过状态。
- **只优化生成任务**：在 Demo 闭环稳定后按课程节奏纳入演化和缺陷修复任务。
- **过早扩展技术栈**：先收集基线和失败案例，再决定是否增加 RAG、MCP、多 Agent 或额外框架。
- **协作知识单点化**：共同评审、交叉演示并维护统一的运行和实验记录。

## 12. 建议的近期工作顺序

1. 在两位组员的电脑上按 `.python-version`、`.nvmrc` 和 `scripts/setup.ps1` 建立一致的本地环境；记录非 Windows 成员的等效安装步骤。
2. 准备一份本地 `requirements.yaml`，用 `--demo` 检查入口、静态页面输出和 SDK 事件/Traceability 文件。
3. 由小组在 ARC-Bench Runner 上运行首个真实任务，确认模型工具调用、依赖安装、目标目录基线及 SDK 刷新行为。
4. 保存平台运行标识、代码版本、实际命令结果和失败原因，按真实环境修订技术选型。
5. 根据 Demo 失败证据修复稳定性，再扩展 Normal Track 与后续任务类型。
