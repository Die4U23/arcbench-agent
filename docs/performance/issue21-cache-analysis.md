# #21：先处理无关写入导致的重复读取

## 历史证据及限制

只读分析 `local-runs/platform-3e5f0811cfe4-20261020/{requests.json,stdout-readable.txt}`，与冻结目录 usage 汇总一致：

| --- | ---: | ---: | ---: | ---: | ---: |

| implementation | 108 | 4,392,146 | 151,897 | 4,042,112 | 350,034 |

| requirement_review | 1 | 30,892 | 19 | 4,608 | 26,284 |

这是历史成功一次，不是当前 Docker 版本或当前 Flash 服务版本的成绩。实现阶段占未命中输入约 88.7%；`read_files` 23 次返回 463,029 字符，`read_file` 21 次返回 68,637 字符。字符不换算为 token，也不能仅凭工具名称确定重复了哪些文件。

请求 54 的上下文由前一请求 235,078 字符降到 148,945，未命中输入 18,336；请求 59 从 213,706 降到 136,848，未命中输入 15,282。这与源码的上下文压缩触发条件相容，但日志没有完整请求序列化和服务商缓存池信息，**不能据此证明具体缓存失效原因**。请求 44 的上下文反而增长，未命中输入仍达 30,942，进一步说明不能只用长度解释缓存。

## 选择的小改动

当前源码在任何有效文件写入后同时清空 `epoch_reads` 与全部 `epoch_file_reads`。因此 `[a,b] → 修改 a → [b,c] → [b,a]` 中，仍在对话内且未变化的 b 会重新返回全文。改动限于：

- 写入后清除精确批次缓存，但文件摘要只失效被写文件，保留同一对话段内其他完整源码证据。
- 每个 `read_files` 都重新读取当前磁盘结果再比摘要，避免相同参数遮蔽外部改动/删除。
- 截断内容不做“完整文件未变”的判定；压缩、控制器回滚及强制源码刷新继续清空/失效原有证据。

没有删除上下文内容、降低验收、改需求或填充 token；文件只在它的完整内容仍可在当前对话段找到且重新读取相同时才返回 unchanged 提示。

## 离线验证

新增覆盖无关写入、重叠批次 `[a,b]→[b,c]→[b,a]`、相同批次外部改动/删除、变更后还原、截断边界；原检查点/压缩/thinking 协议测试继续通过。

使用仓库实际 `prompt_context.py` 和 `repair_policy.py` 作为只读夹具，基线 `d965116` 与候选运行完全相同的 5 次 fake 模型调用和文件操作。最终 a 都为 `value = 2`。累计序列化消息字符由 **118,868 → 116,242**（减少 2,626，约 2.21%）；请求数均为 5。结果保存在 `local-runs/issue21-offline-20261020/read-cache-proxy.json`，没有供应商请求。这只是该固定序列的上下文体积证据，**不是实际缓存命中率、token、费用或完成率改善**。

下一步先用带同一预算/观测保护的 Flash 修复小样本验证执行与记账，再对一个会自然涉及共享文件读取的固定修复任务交错运行基线/候选。不得为了让优化生效额外要求无用读取；小任务若未触发该路径，应如实报告其不具区分力，不花完预算寻找好看的结果。优先报告未缓存输入、总输入/输出、请求数、完整分母及包含失败摊销的每成功任务费用，缓存百分比只是其中一项。
