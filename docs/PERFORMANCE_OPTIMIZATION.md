# ArcBench Agent：Token 与执行速度优化建议

检查日期：2026-09-28。原始问题盘点记录的是修改前的工作区；实施结果与离线曲线见 [性能报告](PERFORMANCE_REPORT.md)。

## 1. 判断与证据边界

当前最值得优化的是模型执行流程：减少重复读取、重复生成、无关修复和重复验收。仅降低总 token 上限只能更早停止，不能保证用更少资源完成任务。

目前已实现批量读写、有界上下文、图片仅在每次实现会话首轮发送、模型请求/总 token 预算、缓存命中统计、截断响应检测、精确局部替换、分层视觉验收、定向修复和模型/工具计时。仍待实施的建议在下文标明；代码位置主要在 `agent/llm.py`、`agent/orchestrator.py`、`agent/tools.py`。

本地历史问题记录 `local-runs/issue-context-compaction.md` 记载：提交 `7299333c877e` 耗时 31 分 59 秒，85 次模型请求、96 次工具调用，累计输入 11,472,350 token、输出 561,486 token，最后未通过。输入约占 95.3%，平均每次请求约 13.5 万输入 token。这是旧运行的二手记录，本次未重新获取平台原始日志，不能用它代表当前代码表现，也不能把累计 token 当作单次上下文或账单金额。

本次没有发起真实模型任务。在检索到的文件中，未找到当前工作区版本完整的逐请求 token、缓存与耗时基线，因此以下区分代码中可确认的问题和需要实验验证的收益。少数旧临时目录存在访问权限问题，不宣称已覆盖所有历史记录。

## 2. 消耗从哪里来

现有主要流程：

```text
每个顶层需求：规划一次 → 多轮实现与工具调用
整个项目：构建/测试 → 结构检查 → 视觉验收
如果失败：所有顶层需求重新进入实现 → 再验收整个项目
```

粗略看，总耗时由模型等待、工具执行、验证以及失败重试组成；累计输入则是每次请求携带内容的总和。例如，每轮新增 2,000 token，连续保留 10 轮，新增历史的累计重传量可达 90,000 token，尚未计算固定指令和任务内容。这只是机制示例，不是本项目实测。

| 已确认的机制 | 代码依据 | 影响 |
| --- | --- | --- |
| 已新增精确局部替换，但批量全文写入仍存在 | `agent/tools.py`：`replace_text()`、`write_files()` | 小改动可避免整文件输出；复杂改动仍可能需要全文写回 |
| 历史超过 100,000 字符后整体压缩 | `agent/llm.py`：`MAX_CONVERSATION_CHARS`、`compact_context()` | 压缩前反复携带文件、工具参数和推理；字符阈值不是 token 阈值 |
| 压缩只保留最近 6 个、每个最多 900 字符的流水摘要 | 同上，`_compact_tool_exchange()` | 没有持久化的需求完成表、文件摘要或未解问题表，可能压掉关键状态并导致重读 |
| DeepSeek 实现阶段默认启用思考 | `ModelClient.__init__()`、`implement()` | 简单机械修改也使用同一种模式；实际延迟占比尚需测量 |
| 每个顶层模块仍独立规划和实现，修复已按证据筛选模块 | `agent/orchestrator.py`：`run_model_agent()`、`_repair_modules()` | 无法归因时回退全部模块；跨模块重新探索仍可能发生 |
| 每次验证扫描多个包并串行执行 build/test | `agent/verify.py`：`verify_project()` | 与模型刚执行的检查可能重复；根脚本若调用子包还可能重复执行 |
| 基础检查通过后才进入视觉验收 | `agent/orchestrator.py`：`verify_current_project()` | 基础失败不会触发视觉模型评审；完整验收仍保留 |
| 所有视觉 case 每次串行评审，之后才执行交互 flows | `agent/visual_acceptance.py`：`verify_visual_acceptance()` | 已通过页面反复付费评审；交互故障较晚暴露 |
| 规划、实现、视觉评审共享 12,000 输出上限 | `agent/llm.py` 三处请求 | 缺少阶段预算；上限本身不代表实际一定生成这么多 |
| 模型/工具已有阶段计时，超时/重试仍使用 SDK 默认值 | `agent/llm.py`：`_create_completion()`、`_record_usage()` | 可以区分模型和工具等待，尚不能细分底层重试或构建耗时 |

本地安装的 SDK 常量为 600 秒默认超时、2 次默认重试。它们是本地依赖证据，不能证明平台依赖或历史慢请求正是这个原因。项目的 24 次请求上限统计客户端调用次数，不等于底层 HTTP 尝试次数。

## 3. 第一优先级：减少不必要工作

### P0-A：补齐可归因的性能记录

在每次请求前后及异常路径记录结构化数据：任务/代码版本、模块、阶段、模型、思考配置、请求耗时、输入/输出/缓存 token、工具名、工具耗时、返回字符数、重读次数、实际变更文件数、验证次数和修复轮数。缺失 usage 必须写为 unknown，不能写成零。运行失败也要在 `finally` 中落盘汇总。

请求次数应区分模型客户端调用和可观察到的 HTTP 尝试。先记录完整请求耗时；以后如引入流式，再区分首个响应片段、首个可见内容和全部完成耗时。流式主要改善进度反馈，不等于降低总计算量。

验收：任意一次运行能说明模型、工具、验证分别花了多久，并列出最贵的请求和反复执行的操作。不要先投入多天做复杂监控界面。

### P0-B：增加局部编辑与按需读取工具

新增 `apply_patch` 或严格的 `replace_text`，保留批量全文写入用于创建新文件。局部修改需校验原文唯一匹配或文件哈希；冲突时返回明确错误，让模型刷新相关片段，禁止模糊匹配后直接写入。

给 `read_files` 增加行范围/字节范围，给 `search_text` 增加路径范围、上下文行数和返回上限。目前搜索可返回 100 条匹配、每条 300 字符；工具层限制应与请求上下文预算一致。缓存文件目录、文件摘要与哈希，文件未变时避免再次传全文。

验收：修改一个已有文件中的少量行，不再要求输出整文件；大文件尾部可读取，补丁冲突不会破坏文件。这通常比继续压缩系统提示词更值得优先做。

### P0-C：把“全项目修复”改成“定向修复”

在一次全局规划中建立轻量映射：需求 → 相关文件 → 检查项。失败后把错误关联到模块，仅把必要需求、最近变更、失败摘要和相关代码交给修复模型。无法定位时先做一次有界诊断，再决定扩大范围。

`VerificationResult.summary()` 当前包含成功和失败检查的输出。传给模型时改为失败项、必要上下文和已通过检查的简短清单；完整日志继续留在磁盘。修复过程中保留跨轮次状态，避免每次重新发现项目。

验收：只有后端某个测试失败时，其他无关模块不进入实现；共享代码改动仍触发相关回归。最终交付继续保留全量验收，不能用局部通过代替整体通过。

### P0-D：验证分层，先便宜后昂贵

执行顺序建议为：结构/清单检查 → 构建及关键测试 → 浏览器交互 → 视觉模型评审。基础失败先修复，再运行昂贵检查。

复用模型工具刚执行的检查结果时，必须匹配源文件状态、锁文件、脚本、命令和必要环境；没有可靠签名就重跑。根脚本与子包是否重复要确认调用关系，不能只按同名脚本跳过。

视觉阶段可在重新截图后，以参考图、实际截图、视口、case 约束、评审提示和模型配置的哈希缓存评审结果。共享样式、参考图或配置变化即失效。交互用例仍需按变更影响执行；不能因为截图未变就假定交互正确。

验收：编译失败不会发起视觉模型请求；无变化的检查不会在每次修复时盲目重复；最终验收证据可追溯到当前文件状态。

## 4. 第二优先级：按任务分配推理与上下文

### P1-A：简单任务走短流程，复杂任务保留推理

针对少量文件、清晰验收条件、无跨模块设计的任务，合并独立规划调用与首轮实现，使用短清单；认证、持久化、多步骤交互和陌生错误保留单独规划与深入推理。任务难度不能只看提示词长短。

当前默认保持 DeepSeek 思考模式，符合本项目的既定选择。`ARCBENCH_IMPLEMENTATION_THINKING=disabled` 是已有的可选配置，但不列为这次性能优化的推荐路径；它不控制规划和视觉评审，也不是所有兼容供应商都承诺支持。

DeepSeek 官方说明，带工具调用的思考模式需要回传相应 `reasoning_content`。优化不能只是删除保留轮次中的这个字段；需要在有效边界结束旧会话，用结构化状态开始新会话，并验证协议。当前按字符串截取的摘要与新策略均需做真实兼容性验证。[官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)

### P1-B：用状态摘要控制上下文，保留稳定前缀

建议上下文由四部分组成：固定规则和任务摘要、文件/需求状态、未解决问题、最近完整工具轮次。压缩时保留已完成要求、当前决策、测试结果、失败假设及相关文件哈希，替代只截取工具返回开头的流水账。

不要每轮重写摘要，使整个前缀不断变化。按阶段或预算边界更新摘要，其间继续追加完整轮次。当前系统指令静态长度为 4,193 字符，工具 schema 序列化后约 2,689 字符；可按任务裁剪无关规则，但不能据此忽视更大的文件与历史负担。

用实际 usage 校准文本 token 估算；工具 schema 也需计入，图片单独估算，不把 base64 字符数当作图像 token。压缩前预估“下一次”请求大小，并处理固定任务本身就超限的情况。请求已经超过预算才压缩，只能限制下一轮。

缓存命中减少重复输入的处理/费用，但不能代替减少无效调用。必须分别比较总输入、未缓存输入、输出和耗时；兼容服务可能有不同缓存行为。[官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)

### P1-C：阶段预算、提前检查和明确结束条件

目前首次默认 checkpoint 在 `turn_index == 16`，即准备第 17 次实现请求时，后续每隔 12 轮触发；全局却只有 24 次模型请求额度，还需要支付规划及视觉验收。大部分预算可能在第一次自动检查之前花掉。

改为“完成一组实质性文件变更后检查”，并设置冷却条件，避免每次微小改动都完整构建。连续若干轮无文件变化、重复读相同内容或错误没有改善时，应重新诊断或明确停止。判断进展要看哈希和有效 diff，不能只数 `written_paths`。

为规划、实现、修复和视觉验收分配预算，并预留最终验收额度。总 token 阈值当前在下一次调用前检查，最后一轮可能超支；应估计下一轮输入并收紧输出额度，保留误差余量。缺失 usage 时需单独提示估算状态。

简单文本任务的实验起点可设为：规划输出约 800–1,500 token、实现每次约 4,000–8,000 token、单 case 评审约 500–1,500 token；这些是待校准的设计参数，并非现有可用配置或平台限额。当前已检查截断信号 `finish_reason`，不再把截断当完成；思考 token 是否占输出额度仍取决于实际接口。

## 5. 第三优先级：控制等待与有限并发

显式设置连接/读取超时、重试上限以及整个任务的截止时间；按阶段衡量长推理所需时间，避免统一压到极短超时。重试应计入耗时与预算，日志注明原因；超时后服务商是否已计费也可能未知。

当前批量脚本工具减少的是模型往返，内部仍然串行。只对无共享输出、端口和测试数据的检查尝试有限并发。视觉请求并发前，先解决预算原子预留与用例状态隔离。先完成去重和定向修复，再考虑并发，通常更容易解释收益和失败。

暂不建议引入多 Agent、向量数据库或复杂调度框架；它们不能直接解决当前重复工作，还会增加调用与状态同步成本。

## 6. 实施顺序与验收方法

| 顺序 | 小步改动 | 必须观察的结果 |
| --- | --- | --- |
| 1 | 已做：模型/工具计时与离线基线；待做：验证计时和更完整的结构化日志 | 能定位最慢和最贵阶段 |
| 2 | 已做：精确局部替换；待做：范围读取与返回裁剪 | 输出量与重复输入下降，编辑正确率不降 |
| 3 | 已做：定向修复和基础失败时暂缓视觉评审；待做：安全的验证结果复用 | 无关模块请求数与重复检查数下降 |
| 4 | 待做：简单任务合并规划、阶段预算，保持思考模式开启 | 成功任务的总成本与耗时下降 |
| 5 | 已做：有界连续上下文；待做：结构化状态与必要的有限并发 | 不破坏协议、验收覆盖和缓存有效性 |

先执行不调用付费模型的确定性离线对照，并公开其指标边界。需要真实收益数据时，先选一个代表性任务，从相同初始项目、任务和依赖开始，固定模型与参数，进行一组有费用上限的 A/B 运行；只有初步结果明确且费用可承受时才扩大到不同任务和重复样本。小样本只能作为探索性证据。

记录端到端完成率、输入/输出/未缓存 token、模型调用次数、模型/工具/验证耗时、修复次数及验收覆盖。小样本报告中位数和范围，不用 3 次运行宣称可靠 P95；失败运行的花费也纳入每次成功交付成本。模型不同或价格缺失时不要编造金额。

首轮目标可设为：在同等功能、结构和视觉验收标准下，简单任务累计 token 降低 30%，端到端时间降低 25%。这是实验目标，不是已实现结果；先建立当前基线，若成功率下降则不接受该方案。

本次已修改运行逻辑。完整测试和离线对照数据记录在 [性能报告](PERFORMANCE_REPORT.md)；这些检查不代表真实模型性能或 ARC-Bench 平台验收。
