# Flash 小任务贯通执行：三次竞赛验证与性能边界

## 结果

最终 v5 同一 ZIP 连续完成三次正式 **5/5**。这表示相同 5 项用例各执行三次，共 15 次用例执行全部通过，不是 15 种独立用例。全部模型请求均配置并记录为 `deepseek-flash`，没有请求 Pro。

对照为原冻结包一次成功运行，不能将本次小样本差异当作通用性能或因果证明。包含最差第三轮后，平均总 token 下降 **43.95%**，平均未命中输入下降 **64.87%**；加权输入命中率从 **93.9507%** 到 **96.1767%**，增加 **2.2260 个百分点**，没有达到 99%。

## 具体改动

- 完整需求不超过 24,000 字符、包含 2–4 个有描述的叶子、原模块覆盖全部需求 ID 时，共用一个 ROOT 规划和实现上下文。保留原始需求对象、场景及所有 ID；大任务和不完整输入维持原调度。
- 复用仍在当前上下文中的完整源码证据；真实磁盘读取仍执行，内容变化、回滚、截断和压缩移除证据后失效。显式单文件读取保留刷新语义。
- 周期检查或按需 `verify_candidate` 通过后立即交回控制器；按需通过后连同一批剩余可选编辑也不执行。独立完整边界仍执行，边界失败不得被之前的诊断通过覆盖。
- 仅在完整成功、全部输入指纹与回滚版本未变时，一次性复用紧接着的完整边界结果。预算终止、部分结果、失败和不可用指纹不能绕过正常检查。
- 合并同轮精确匹配的根脚本委托；含额外命令、hook、参数或无法可靠解析的形式保持真实执行。已知失败直接传给后续修复，避免重新发现。
- 需求审核保持完整源码覆盖与严格原文引用验证。纠错信息明确无效引用的节点与原引用；审核明确撤回自己的缺陷时拒绝结果，不允许据此修改生产代码，也不自动改为通过。仍只允许一次纠错。
- 明确 Flash 模型别名白名单并拒绝 Pro；生成提示要求真实应用/API 必要流程、有效夹具和有界测试范围，不删除已有测试或削弱验收。

## 未解决部分

1. **C1 的需求审核仍未验证。** 两次审核都给出自相矛盾的缺陷，控制器拒绝并保留失败；构建、自测与平台 5/5 通过。C2 审核通过，C3 纠错一次后通过。不能宣称三次所有本地审核都通过。
2. **自测反复修补尚未消除。** C3 出现长输出截断、三次替换工具错误，以及至少 11 次显式脚本工具调用失败；其总 token 只比基线少 7.04%。最高命中率对应最昂贵候选，说明仅提高比例不能代替减少无效工作。
3. **过早检查仍存在。** C2 在测试文件未写完时检查失败，后续补齐后通过。根脚本未匹配安全复用规则的形式也会保持真实执行；不能宣称所有重复检查都已消除。
4. 三个样本都没有记录源码内容替换为复用标记的事件，不能把真实收益全部归因于该缓存机制。观察到的共同变化是一套小任务规划/实现上下文、较少的读取和请求，以及通过后的控制器交接。
5. 同一任务仅三次候选、一次成功基线；缓存温度与生成随机性影响结果。没有新的 Playground 30/30，也没有 Claude Code 同条件对照，[issue #21](https://github.com/Die4U23/arcbench-agent/issues/21) 继续开放。
